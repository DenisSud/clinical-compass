# Клинический компас

Продукт для врача, который ведёт пациента с тревожной и депрессивной симптоматикой между
приёмами: опросники, дневник самочувствия, отметки о приёме препаратов, сигналы и план лечения
в одной карточке. Клиническое действие всегда за врачом: система не назначает, не отменяет и не
направляет сама. Роли две: пациент и врач; у врача есть специальность, терапия или психиатрия, и
она задаёт этап пациента: у терапевта скрининг, у психиатра терапия (передача одним действием,
отдельного переключателя этапа нет).

## Как это устроено

**Инструменты.** Шкала это файл, а не код: вопросы, ключ подсчёта, полосы тяжести и источник
(`server/instruments/*.json`). Набор шкал на этапе задаёт `content/instrument-statuses.json`.
На скрининге пациент заполняет PHQ-9; на терапии HADS двумя частями (тревога и депрессия) и UKU
по побочным явлениям. Сумму и полосу этих шкал видит только врач: в пациентском ответе нет ни
`total`, ни `band`.

**Приём и HDRS-17.** Психиатр назначает следующий приём из карточки пациента; пациент видит дату
и может включить напоминание на почту (письма продукт не отправляет, хранится только
предпочтение). После приёма психиатр заполняет HDRS-17: это шкала врача, пациент её не заполняет
и не видит.

**Правила и сигналы.** Правило это условие на наших полях, вывод для врача и обязательная ссылка
на источник; правила живут файлами в `content/rules/`, врач может добавить своё правило
наблюдения. Сигнал это вопрос, на который врачу надо посмотреть, а не указание: у сигнала есть
уровень, источник и обязательный исход разбора, критический сигнал без исхода не закрывается.

**Что видит врач.** Список пациентов и карточка пациента с разделами «Обзор» (приём,
приверженность, варианты терапии), «Наблюдение» (правила врача, обязательные факты, сигналы
пациента), «План» (черновик, подтверждено, архив), «Переписка» и «Данные» (опросники, дневник,
график дневника). Пациент видит свои сырые ответы, даты, план и сообщения: без баллов, полос и
трендов.

## Стек

TypeScript по всему репозиторию. Сервер: Fastify, SQLite через better-sqlite3 и Drizzle,
миграции это SQL-файлы в `server/db/migrations`. Клиент: React, Vite, обычный CSS с токенами в
`web/src/styles/tokens.css`. Схемы и контракты по границе API лежат в `shared/`, проверка через
zod. Тесты: vitest.

## Как запустить

```bash
npm install
npm run dev
```

`npm run dev` поднимает API на `:3000` и Vite на `:5173` с проксированием `/api`. Миграции
применяются при первом обращении к базе, отдельный шаг не нужен. Демо-данные (врач и два
привязанных пациента) создаются командой `npm run db:seed`.

Сборка и рабочий запуск:

```bash
npm run build     # SPA собирается в server/public
npm run start     # NODE_ENV=production tsx server/index.ts, API и SPA на одном порту
```

Переменные окружения (см. `.env.example`):

| Переменная | Что задаёт |
| --- | --- |
| `PORT` | порт HTTP-сервера, по умолчанию 3000 |
| `SQLITE_DB` | путь к файлу SQLite, по умолчанию `var/app.db` |
| `SEED_DOCTOR_EMAIL` | адрес демо-врача для `npm run db:seed` |
| `SEED_PASSWORD` | пароль демо-доступа |

Кроме них сервер читает `HOST` (по умолчанию `127.0.0.1`; для развёртывания за обратным прокси
его задают явно). Полезные команды есть и в `Makefile`: `make dev`, `make test`, `make seed`,
`make db-reset`.

## Как проверить

```bash
npm test           # vitest, тесты маршрутов, правил, шкал и расписания
npm run typecheck  # tsc для клиента и для сервера
npm run play       # площадка логики на настоящих модулях
```

Площадка это интерактивная проверка того, что увидит врач. Пример:

```
> статус психиатр
> шкала uku все=1
```

Первая команда показывает специальность, выведенный из неё этап и набор шкал, вторая отправляет
UKU по всем 48 пунктам: видно, что общей суммы у шкалы нет и карточки по сумме не появляется.
Готовые сценарии проходятся командой `сценарий N` (`сценарий 2` это критический пункт PHQ-9),
`help` печатает все команды. Отказы продукта площадка воспроизводит так же, как маршрут: будущее
время, пропуск без причины, неполный опросник.

## Что ещё не сделано

Перечисленное описано в `SPEC.md`, но в коде этого нет:

- доставка писем и напоминаний: настройка напоминания к приёму хранится, письма не уходят;
- разбор свободного текста дневника и сопоставление побочных явлений с профилями препаратов
  (задачи модели, результат всегда «возможно» и только для врача);
- графики динамики по инструментам: сумма как точка и полоса как зона (сейчас есть только график
  дневника);
- предупреждение о дозе вне рекомендуемого диапазона: ввод не блокируется, врач получает
  предупреждение.

Порядок работ задаёт `SPEC.md`, причины решений лежат в `decisions.md`, открытые вопросы в
разделе «Открыто» там же.
