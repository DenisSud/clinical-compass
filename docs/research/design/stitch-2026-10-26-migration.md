# Экспорт Stitch 2026-10-26: карта экранов и план миграции

Дата: 2026-10-26. Источник: `var/screens/stitch-2026-10-26/` (12 папок, в каждой
`code.html` + `screen.png`).

Рамка: `DESIGN.md` §2 (безопасность, «пациент не видит интерпретаций», семантика
сигналов, врач не теряет информацию, ошибка не выдаётся за пустоту), `GLOSSARY.md`
(«ведущий врач», «привязка», «код привязки», «результат разбора», «не спрашивали»),
`web/src/styles/tokens.css` (единственный источник цвета и шкал).

Дизайн-система экспорта — палитра, типографика, компоненты, сверка с нашим кодом —
разобрана отдельно: `docs/research/design/stitch-2026-10-26-system.md`. Здесь её нет:
этот файл про экраны и про то, кто и в каком порядке их трогает.

Что проверено и чем:

- `npx vitest run` — 25 файлов, 273 теста, все проходят (5.5 с);
- `npm run typecheck` — чисто; `npm run build` — 131 модуль, CSS 17.47 kB, JS 389 kB;
- `screen.png` в `_1`–`_6` — не картинки: 28 байт ASCII, содержимое
  `<FIFE Image failed to fetch>`. **Шесть экранов пациента визуально проверить
  нельзя, только по `code.html`.** В `_7`–`_12` PNG настоящие (949×1600 … 1600×1415);
- все утверждения ниже — из `code.html` (класс, hex, строка) или из PNG `_7`–`_12`.

Поправка к постановке задачи: `_1` — это дневник (в `<h1>` «Дневник самочувствия»),
«Сегодня» — `_2`. Дальше экраны названы по факту, папка указана рядом.

## 0. Сводная карта: 12 экранов и один вердикт на каждый

новых данных; **работа** — нужны данные или экран, которых у нас нет; **не берём** —
экран в экспорте противоречит правилам продукта.

## 1. Экраны по одному

### 1.1. `_1` — «Дневник самочувствия» (пациент)

**Что на экране.** `<h1>Дневник самочувствия</h1>` (headline-lg 24 px), подзаголовок
«Хронологический регистр субъективной оценки состояния и заметок» (body-sm). Строка
`Всего записей: 4` (label-sm 11 px uppercase) и кнопка «Новая запись»
(`h-11 px-space-md rounded-xl bg-surface-container`). Карточка записей:
`rounded-xl bg-surface-container-lowest` с рамкой `1px #e8d5c5`; каждая запись —
`article p-space-md` с `border-bottom: 1px solid #e8d5c5`; дата `body-sm
text-on-surface-variant` («28 октября 2026, 21:15»), значение справа
`font-headline-md … tabular-nums` = «6 / 10» (18 px), текст записи body-md. Внизу
«Загрузить предыдущие записи» (`w-full h-11 bg-surface-container-high`).

**Наш файл.** `web/src/PatientHome.tsx:224-249` — вкладка «Дневник»; сама запись
создаётся на вкладке «Сегодня» через `DiaryForm.tsx`.

**Что меняется.**

- Разметка: записи становятся карточкой с рамкой `--border-hairline` и разделителями
  между строками, а не `borderTop` на каждой `li` (`PatientHome.tsx:238`).
- Классы: `.diary-entry` / `.diary-entry__head` вместо инлайновых
  `borderTop/paddingTop`; голова записи `justify-content: space-between` — дата слева,
  значение справа. Сейчас значение первым (`<strong>{entry.value}</strong>`,
  `PatientHome.tsx:239`).
- Текст: подзаголовок «Хронологический регистр…» **не берём** — канцелярит, ничего не
  добавляет к заголовку (§2.4 не требует пояснять очевидное).

**Что из экспорта брать нельзя.**

- «Всего записей: 4» — счётчик, который ничего не решает. Не нарушение (§2.2 про
  оценки), но и не нужен: у нас список и так весь на экране.
- «Новая запись» — второй вход в ту же форму: запись одна на день, форма живёт на
  «Сегодня» (`PatientHome.tsx:209`). Два входа в одно действие — §3.10.
- «Загрузить предыдущие записи» — API пагинации нет: `fetchMyDiary` отдаёт весь список
  (`web/src/api.ts:160`). Кнопка изобрела бы поведение.
- Формат «6 / 10» оставляем как у нас (`PatientHome.tsx:201, 241`): это собственный
  ответ пациента, не оценка системы (§2.2). Но 18 px headline и `tabular-nums` не
  переносим — значение не должно быть самым громким на экране.

  **клиента нет**: в `web/src/api.ts` нет ни `/prescriptions`, ни `/doses`. Сейчас
  «Сегодня» рендерит пункты плана (`PatientCheckinItem`, `shared/contracts.ts:273-279`;
  `TodayPlan.tsx:60`) без времени.
  Это не косметика, а новый экран таблетницы — отдельный тикет (§3.5).
- «Сохранить», активная при невыбранной оценке: у нас кнопка неактивна до выбора
  (`DiaryForm.tsx:84`) и сказано, чего не хватает (`:63`).
- Выбранная кнопка «Пропустил» красится в синий как «выбор»: у нас она открывает поле
  причины, а не фиксирует пропуск.

## 3. План миграции волнами

### 3.1. Правило, ради которого всё разбито

**В одной волне два исполнителя не пишут один файл.** Файл меняет один человек; если
файл нужен второму — он ждёт следующей волны. Общие файлы (`styles.css`, `ui.tsx`,
`PatientHome.tsx`, `PatientDetail.tsx`, `api.ts`, `tokens.css`) — самые опасные, поэтому
волна 0 раздвигает их так, чтобы дальше каждый экран жил в своём файле.

`tokens.css` в волнах **не трогаем вообще**: палитра уже решена (#29, #32), а любое
значение из экспорта — это новая задача с пересчётом контраста.

### 3.2. Волна 0 — раздвинуть общий файл (один исполнитель, без изменения вида)

Это перемещение, не правка. Критерий приёмки: `git diff --stat` показывает переименования
и новые файлы, но ни одного изменения разметки; `npm run typecheck` и `npm run build`
зелёные; `npx vitest run` — 273.

**CSS.** `web/src/styles.css` (1197 строк) → пять файлов рядом с `tokens.css`:

| Новый файл | Строки сегодня | Что внутри |
| --- | --- | --- |
| `styles/base.css` | 1–354 | reset, `html/body`, `:focus-visible`, `.app`, `.topbar`, `.page*`, `.tabs*`, `.card`, `.section-title`, `.stack`, `.row`, `.muted`, `.hint`, `.notice*`, `.load-error`, `.button*`, `.choice`, `.details-summary` |
| `styles/patient.css` | 387–398, 1193–1197 | `.diary-scale` (+ медиа 600 px), `.facts-invite` |
| `styles/doctor.css` | 355–386, 400–406, 407–885 | `.disclosure*`, `.code`, сигналы (407–692), правила наблюдения (693–787), пациенты (788–885) |
| `styles/facts.css` | 1078–1192 | блок «блокирующие факты» целиком: `.facts*`, `.fact*`, `.facts-gaps*`, `.facts-report*` — им пользуются оба экрана, поэтому он один файл, а не половина в пациенте и половина у врача |
| `styles/auth.css` | 886–1077 | вход (#55) |

`styles.css` становится только списком импортов (порядок фиксирован):

```css
@import "./styles/base.css";
@import "./styles/patient.css";
@import "./styles/doctor.css";
@import "./styles/facts.css";
@import "./styles/auth.css";
```

`main.tsx:4-5` не меняется: `tokens.css`, затем `styles.css`. Vite склеит импорты в один
файл — сейчас это 17.47 kB на сборке.

Что нельзя разрывать при переносе:

- блок `@media (forced-colors: active)` (внутри 407–692) — он про сигналы;
- `.facts-gaps__list, .facts-report__list` — один селектор на два экрана (1161–1167),
  поэтому он целиком в `facts.css`;
- правила одного селектора должны остаться в одном файле: сегодня `.signal--closed`
  встречается трижды (базовый, `forced-colors`, внутри `.closed-group`), и порядок
  между ними — часть смысла.

**JSX.** Две точки сборки делятся на вкладки, чтобы следующие волны не спорили за файл:

- `PatientHome.tsx` → `web/src/patient/TodayTab.tsx`, `DiaryTab.tsx`,
  `QuestionnaireTab.tsx`, `PlanTab.tsx`, `DoctorTab.tsx` (вкладка «Мои данные» —
  по-прежнему `<FactsForm />`, своего файла не нужно);
- `PatientDetail.tsx` → `web/src/doctor/OverviewTab.tsx`, `WatchTab.tsx` (туда же
  переезжает `PatientSignals`), `PlanTab.tsx`, `MessagesTab.tsx`, `DataTab.tsx`.

**Важно:** загрузки остаются в родителе (`PatientHome`, `PatientDetail`), вкладки
получают `Load<T>` и колбэки пропсами. Иначе каждая вкладка начнёт грузить при
монтировании — это изменение поведения, а волна 0 поведение не меняет.

### 3.3. Волны 1–5: кто, что, чем владеет

Обозначения: **A** и **B** — два исполнителя одной волны, работают одновременно.
«CSS» — файл стилей, который волна имеет право менять; остальные файлы стилей в этой
волне заморожены.

| Волна | A | B | CSS волны | Выход |
| --- | --- | --- | --- | --- |
| 1 | Оболочка пациента и дневник: `ui.tsx` (TopBar), `PatientHome.tsx` (список вкладок), `patient/TodayTab.tsx`, `patient/DiaryTab.tsx`, `DiaryForm.tsx`, `TodayPlan.tsx` | Сигналы: `SignalsPanel.tsx` | A: `base.css`, `patient.css`; B: `doctor.css` | `_1`, `_2`, `_8` |
| 2 | Список пациентов и приглашение: `DoctorHome.tsx` | Опросник: `patient/QuestionnaireTab.tsx`, `Phq9Form.tsx` | A: `doctor.css`; B: `patient.css` | `_9` (левая колонка), `_3` |
| 3 | Приверженность: `AdherenceTable.tsx`, `doctor/OverviewTab.tsx` | Переписка: `MessageThread.tsx`, `patient/DoctorTab.tsx`, `doctor/MessagesTab.tsx` | A: `doctor.css`; B: `patient.css` | `_9` (календарь), `_4`, `_11` |
| 4 | Наблюдение: `WatchPanel.tsx`, `doctor/WatchTab.tsx`, `PatientFactsPanel.tsx` | План: `PlanPanel.tsx`, `patient/PlanTab.tsx` | A: `doctor.css`, `facts.css`; B: `patient.css` | `_7`, `_10` |

Почему именно так:

- `ui.tsx` и `base.css` меняются один раз, в волне 1, и после неё заморожены. Всё, что
  нужно оболочке (липкая шапка, метка выбранной вкладки), делается там же, а не
  «попутно» в волне 3.
- `MessageThread.tsx` — общий для пациента и врача, поэтому он весь в волне 3, у B.
  Волна 3 A не имеет права его открывать: если нужна правка пузыря — это запрос на
  волну 3 B.
- `AdherenceTable.tsx`, `PlanPanel.tsx`, `DataTab.tsx` набраны инлайновыми стилями —
  это позволяет ставить их в пару к волне, которая владеет CSS.
- Каждая волна заканчивается одним и тем же: `npm run typecheck`, `npm run build`,
  `npx vitest run`, затем восемь вопросов чек-листа `DESIGN.md` §5 — глазами.

### 3.5. Вне волн — отдельные тикеты

Это не дизайн, а продукт. Волны их не касаются, чтобы миграция вида не превратилась в
разработку функций.

1. **Экран таблетницы.** `_2` показывает приём по времени (`08:00`, `20:00`).
   Данные и роут есть (`server/routes/prescriptions.ts:166-200`,
   `shared/contracts.ts:363-378`), клиента нет. Нужен `api.ts` + экран + стили, и
   решение, заменяет ли он отметки плана (`/api/checkins`) или живёт рядом.
2. **Расхождение приверженности.** Таблица считает по пунктам плана
   (`/api/patients/:id/checkins`), а правило пропусков — по назначению
   (`server/prescriptions/schedule.ts`). Пока это два источника об одном.
3. **Сумма PHQ-9 в реестре пациентов** (`_12`): либо строка называет дату и диапазон,
   либо суммы там нет.
4. **Поле имени.** `name` есть в контракте и схеме, но никто его не заполняет — поэтому
   «Анна» в шапке пациента неоткуда взять. Либо экран имени, либо шапка без имени.

## 5. Риск по волнам

**Главное про тесты.** `vitest.config.ts:4-6` включает только `server/**/*.test.ts` и
`shared/**/*.test.ts`; в `web/` тестов нет. Значит: **ни одна волна не может сломать 273
теста, пока не трогает `server/` или `shared/`**, — а по плану она их не трогает.
Обратная сторона: ошибку вёрстки ничто не поймает, кроме `typecheck`, сборки и глаз.
Единственная механическая защита от регрессии интерфейса — `npm run typecheck`
(`tsconfig.json` включает `web/src`) и `npm run build`.

| Волна | Тесты (273) | typecheck / build | Клинический риск | Что смотреть руками |
| --- | --- | --- | --- | --- |
| 0 | не могут упасть | typecheck ловит несовпадение пропсов при разрезании вкладок; build — порядок CSS; новых зависимостей нет | разрез вкладок может изменить момент загрузки — если загрузки уедут в вкладки, пациент увидит «нет данных» там, где просто ещё не грузили (§2.5) | все 12 экранов до/после: те же блоки, тот же порядок, те же тексты; CSS-бандл ~17.5 kB |
| 1A | не могут | `ui.tsx` меняет `TopBar` — он же у врача: typecheck поймает пропсы, а вид врача — нет | шапка и вкладки общие для двух ролей; ошибка в `Tabs` задевает кабинет врача; липкая шапка съедает высоту на телефоне (в экспорте 144 px) | кабинет врача после правки шапки; вкладки на 375 px (перенос строк, `styles.css:185-228`) |
| 1B | не могут | только `SignalsPanel.tsx` + `doctor.css` | самый высокий: заголовок группы не должен отобрать акцент у критической карточки; счётчик уровня не красится красным; «Закрыть» без результата не появляется | серый скриншот: критическая карточка по-прежнему самая громкая (§2.3); закрытый сигнал без цвета; `@media (forced-colors)` |
| 2A | не могут | `DoctorHome.tsx` | код привязки не должен снова стать крупнейшим текстом кабинета (§3.1, §3.4) | первая вкладка врача: сигналы выше кода; перевыпуск с подтверждением |
| 2B | не могут | `Phq9Form.tsx`, `patient.css` | соблазн визарда: девять пунктов не режутся, девятый не прячется (§2.1, §2.4) | весь опросник до конца без прокрутки назад; неактивная отправка объясняет, чего не хватает |
| 3A | не могут | `AdherenceTable.tsx` (инлайн-стили) | «нет сведений» не должно читаться как пропуск; процент не появляется | 14 дней, три состояния в сером; сбой загрузки — текст, не пустая сетка |
| 3B | не могут | `MessageThread.tsx` общий для двух ролей | перепутать «Пациент» и «Вы (врач)» на экране врача | обе переписки; пустой список; ошибка отправки |
| 4A | не могут | `WatchPanel.tsx`, `PatientFactsPanel.tsx`, `doctor.css`, `facts.css` | «Приостановить» у встроенного правила; заливка факта громче сигнала; «не отмечено» ≠ «нет» | порядок «правила → факты → сигналы» (`PatientDetail.tsx:216-237`); три состояния фактов |
| 4B | не могут | `PlanPanel.tsx` | «Остановить»/«Изменить» без маршрута; черновик не должен стать похож на подтверждённое | пациент не видит черновик (`PatientHome.tsx:344-348`); «Подтвердить» только у черновика |
| 5A | не могут | `DataTab.tsx` | сумма и диапазон — только у врача; «критический пункт» не превращается в оценку | таблица на 375 px, длинные диапазоны |
| 5B | не могут | `FactsForm.tsx`, `patient.css`, `facts.css` | предвыбранный ответ факта — подстановка клинических данных | форма открывается пустой; «Не знаю» доступно на каждом вопросе; сбой сохранения не стирает введённое |

Что может сломать сборку, кроме typecheck: только порядок `@import` в волне 0. Если
`facts.css` поставить раньше `base.css`, правила `.fact*` могут проиграть базовым
сбросам — поэтому порядок в §3.2 зафиксирован и меняется отдельным коммитом с
обоснованием.

`npm run play` (площадка логики) волнами не затрагивается: она импортирует
`server/rules/registry`, `server/instruments/engine`, `server/prescriptions/schedule`,
а миграция живёт в `web/`. Если площадка начала падать — значит, кто-то тронул сервер,
и это ошибка волны, а не шума.
