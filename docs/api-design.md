# apps/api: интерфейс прикладного модуля

Записано после design-it-twice: четыре независимых проекта одного модуля при
разных ограничениях, затем сравнение. Решение — гибрид, ниже сказано, что взято
и что отвергнуто.

Всё, что ниже, — про **интерфейс**: не только сигнатуры, но и инварианты,
порядок, режимы ошибок и стоимость. Глубина = рычаг на интерфейсе, а не
отношение строк реализации к строкам интерфейса.

## Что было дано всем четверым

- `compass/` — готовые чистые модули (instruments, knowledge, ai), 42 теста.
- Postgres — local-substitutable.
- Запрет на клиническое действие без подписи врача; две роли; инвайт; append-only
  аудит; алерты переживают перезапуск; «обязательно»/«желательно»; каталог РФ.
- Пять поверхностей, из них две несут почти весь трафик: список врача и приём.

## Четыре проекта

**1. Минимальный интерфейс (≤3 точки входа).** Один модуль `Clinical`:
`view(actor, query)`, `commit(actor, intent, key)`, `advise(actor, question, patient)`.
Закрытые объединения `Intent` (9 членов) и `Query` (5 членов); `SignAppointment` —
единственный член, дотягивающийся до терапии. Рычаг огромный: авторизация,
идемпотентность, аудит, триаж, состояние алертов и подпись живут за одним швом.

**2. Максимальная гибкость.** Семь модулей: `identity`, `intake`, `signals`,
`rules`, `therapy`, `feed`, `audit`, и композиционный корень. Лучшая идея:
`Scoped[Actor]`, который умеет создать только `identity`, — «врач со живой связью
с этим пациентом» становится предусловием конструирования, а не проверкой,
размазанной по обработчикам. Плюс `feed`, у типа карточки которого **нет поля**
под сумму: D5 обеспечивается типом.

**3. Под частого вызывающего.** Один модуль, семь методов: `queue`,
`commit_appointment`, `card`, `patient_today`, `submit_questionnaire`,
`send_message`, `publish`. Единственный проект, который посчитал стоимость:
наивно 6 запросов на пациента → 150 пациентов ≈ 900 round-trip, 200–900 мс, то
есть мимо порога Доэрти; проекция — 3 запроса плюс ~3 мс на merge, 10–20 мс.
Закрытый набор ошибок `Rejected(kind, field, message)`, чтобы гейт подписи
показывал причину, а не спиннер.

**4. Порты и адаптеры.** Порт `Clinic`, семь методов, `SignalKey = (patient,
source, code, item, kind)` — стабильный ключ алерта, переживающий правку правил.
Вердикт по главному вопросу: сигналы выводить на чтении, алерты персистить.

## Что сошлось независимо у всех четырёх

Это и есть сигнал качества — совпадение не сговорено:

1. Один путь записи клинического состояния. Подпись — гейт, а не шаг.
2. Идемпотентность на `submission_key` у всех пишущих вызовов.
3. Токен снимка для списка (`revision` / `expect: Seq`): строка не двигается под курсором.
4. Алерт — персистентное состояние с жизненным циклом, не сообщение.
5. У пациентских типов **нет поля** под сумму/полосу/тяжесть.
6. Аудит добавляется в той же транзакции, только вставкой.
7. `compass/` импортируется напрямую, без обёртки.

## Спорный вопрос закрыт

**Выводить сигналы на чтении, персистить алерты** (проекты 3 и 4 пришли к
одному, разными путями).

- Материализовать сигналы — значит купить два дефекта: правка правила требует
  бэкфилла, а непроверенный алерт становится персистентным клиническим
  утверждением, которого никто не подписывал.
- Выводить на чтении дёшево: подсчёт микросекундный, ключ сортировки чистый.
- **Но** модельный скрининг свободного текста — не чистый и не дешёвый: он
  вызывается **один раз при записи**, и его кандидаты лежат рядом с ответом.
  Повторно на чтении он не выполняется никогда.
- Алерты персистятся, потому что им нужны жизненный цикл, аудит и переживание
  перезапуска. Строка алерта хранит доказательство **в том виде, в каком оно
  было на экране** при подтверждении, — история остаётся читаемой, даже когда
  правило, породившее её, изменилось.

## Выбранный интерфейс

Один модуль `Clinical`, девять методов. Девять, а не три: три метода с
пятнадцатью вариантами внутри — это широкий словарь за узкой вывеской, глубина
там номинальная, и проект 1 сам это признал.

```
queue(actor, *, since_revision=None)            -> Queue
card(actor, patient_id)                          -> CaseFile
feed(actor)                                      -> Feed
commit_appointment(actor, draft, *, submission_key) -> Appointment
publish(actor, appointment_id, fields)           -> None
submit_response(actor, assignment_id, answers, *, submission_key) -> Assessment
send_message(actor, scope, text, *, submission_key) -> Message
acknowledge(actor, signal_key, action, note="")  -> Alert
advise(actor, patient_id, question)              -> Advice
```

Аудит читается не клинической операцией: это проекция append-only таблицы через
порт хранилища, отдельным маршрутом.

### Инварианты

1. Полномочия выводятся из таблицы связей на каждом вызове. Роль в `Actor`
   ничего не разрешает.
2. `commit_appointment` атомарен: авторизация → валидация по каталогу и чистым
   правилам → запись приёма, назначений, направления, плана → закрытие алертов →
   аудит. Любая ошибка не пишет ничего.
3. **Внутри `commit_appointment` нет вызова модели.** Валидация — каталог плюс
   чистые правила. `advise` — отдельный вызов, вне транзакции; модель не может
   ни задержать подпись, ни изменить состояние.
4. Подпись — гейт: клинические поля существуют только в подписанном приёме и
   после подписи неизменяемы (изменение = новый приём).
5. `publish` — единственный способ довести до пациента. По умолчанию не
   опубликовано ничего.
6. `queue` сортирует только ключом `triage.merge`; адаптер может разрешить
   равенство по времени **внутри** полосы и не может пересортировать полосы.
   `since_revision` фиксирует снимок.
7. `submit_response` идемпотентен по ключу; `commit_appointment` — оптимистичен
   по `expected_revision`.
8. Алерты не удаляются. `resolved` — состояние, не удаление.
9. Пациентские типы не имеют полей под сумму, полосу, тяжесть.
10. `advise` не бросает при отказе модели: возвращает `Advice(degraded=True,
    reason=...)`, и приём подписывается без подсказки.

### Режимы ошибок

`Rejected(kind, field, message)` с закрытым `kind`: `role`, `not_your_patient`,
`unsigned`, `unknown_drug`, `dose_not_in_label`, `contraindicated`,
`needs_acknowledgement`, `obligation_downgraded`, `stale`, `conflict`,
`definition_changed`, `incomplete`. Смысл: гейт подписи показывает **причину**,
а не «что-то пошло не так». Инфраструктурный отказ — не `kind`, он летит наверх
как 5xx.

## Что взято у кого

| Взято | У проекта | Почему |
|---|---|---|
| Плоский набор методов под поверхности | 3 | три метода с 15 вариантами — не глубина, а широкий словарь |
| Расчёт стоимости списка | 3 | единственный, кто посчитал round-trip и порог 400 мс |
| Закрытый `kind` ошибок | 3 | гейт подписи обязан называть причину |
| `SignalKey` как стабильный ключ алерта | 4 | переживает правку правил, не ломает историю |
| Вердикт «сигналы на чтении, алерты персистятся» | 3 + 4 | сошлись независимо |
| `Scoped[Actor]` как предусловие | 2 | но **внутрь** модуля: при одном модуле проверка и так одна |
| `feed` с типом без поля суммы | 2 | D5 обеспечивается типом, а не дисциплиной |
| `advise` вне транзакции | 1 + 3 | модель не должна задерживать подпись |

## Что отвергнуто

- **Три метода с закрытыми объединениями.** Словарь из 14 типов, который
  вызывающий обязан выучить, — это интерфейс, и он не маленький.
- **Семь публичных модулей.** 28 методов ради гибкости, которая понадобится
  позже, чем через десять дней. `Scoped[Actor]` решает ту же задачу внутри
  одного модуля.
- **Обёртка над `compass/`.** У чистых модулей нет второй реализации; обёртка —
  шов, за которым ничего нет.
- **Кэш очереди.** 15 мс на 150 пациентов. Кэш покупает класс багов инвалидации
  и может пересортировать снимок, который UX запрещает. Пересматривать выше
  ~500 пациентов.
- **Материализация сигналов.** См. выше: бэкфилл и неподписанное утверждение.

## Проверка удалением

Убрать `Clinical` → авторизация, идемпотентность, аудит, триаж, гейт подписи и
публикация расползаются по десяти обработчикам, и каждый из пяти инвариантов
придётся поддерживать в пяти местах. Модуль зарабатывает своё место.

## Что осталось тонким, честно

- Четыре метода из девяти — почти транзитные. Первым расширится
  `submit_response`, когда у C-SSRS появится ветвление и понадобится `next_item`.
- Сортировка пересчитывается на каждом чтении: правка `triage.py` меняет порядок
  в очереди молча. Закрыто тестами, но не типами.
- `acknowledge` почти табличный. Оставляем маленьким.
